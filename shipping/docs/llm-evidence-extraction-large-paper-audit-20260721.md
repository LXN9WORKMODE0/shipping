# 大论文 Evidence 抽取稳健性审计（2026-07-21）

## 结论

当前 Card-to-LLM 的输入隔离、Token 规划、Non-think 路由、原始响应存档和失败账本已经可用；但“一次生成、严格校验、任一批失败即不综合”的 Evidence 抽取策略尚不能稳定处理大论文。

82 Card 论文在 v3 规划下被拆成19个章节批次。原始运行13批通过、6批失败；修正3类确定性数值规范化缺口后，原始响应可离线判定为16批有效、3批仍有真实合同违约。由于历史运行不可变，它仍保持 `partial`，没有进入综合。

缩小批次解决了24 Card 表格密集批中单个 Evidence 使用12条 citation 的问题，但没有消除数值漏引和跨 Card quote_id 错配。继续缩到逐 Card 不会解决表头、单位和数值绑定问题，也会放弃论文/章节上下文，因此不建议继续靠缩批推进。

## 本轮代码变化

1. Evidence 合同
   - 每张 Card 最多12条 Evidence，单条 Evidence 最多8条 citation。
   - claim 中的每个阿拉伯数字必须出现在所选逐字引文中。
   - `建议、考虑、可能、预计、计划、约、至少、至多、仅、尚未` 等关键限定词不得被删除。
   - 数值合同识别 TeX `\%`、数学片段分隔数字和含 `\tag/\cdot/\forall` 的公式行。
   - 只有 source 坐标连续的两个已选 quote 才能拼接被候选边界切开的数值。

2. 引文候选
   - 句界选择不再把数字之间的 `.` 或 `,` 当作分割点，避免把 `677.2` 切成 `677.` 和 `2`。

3. Evidence claim 门禁
   - 完整 claim 分句在同一逐字引文中按顺序出现时，由代码形成 `passed_quote_containment` 证明。
   - 不使用相似度，不跨引文拼接；同句前缀或分句间出现条件、转折、模态词时不形成证明。

4. 字段职责
   - `core_findings` 明确覆盖政策分析、SWOT和案例研究中作者用于构成机会、威胁、现状或对策依据的政策条件、市场预测和外部约束。
   - 字段职责核验输入增加 `study_type` 和 `research_focus`。

5. 大论文规划
   - model profile 升级为 `llm.model_profile.v3`。
   - 新增 `large_paper_evidence_batch_max_cards=12`。
   - 小中型论文只要整体 Token 预算允许，仍整篇单批；只有整篇超预算的大论文章节批次受12 Card身份上限约束。

## 真实运行结果

### 15 Card 中型论文

论文：`三峡工程给川江航运带来的机遇及对策`

- `medium15-20260721`：claim 双轮门禁出现3项不一致。
- `numeric1`：模型为一张表输出5条 citation，暴露旧 citation 上限过低。
- `numeric2`：暴露百分号正则边界问题。
- `numeric3`：暴露 MinerU 公式 `$P = 5 ~ 1 5 2$` 的 OCR 数字分隔。
- `numeric4`：输出31条 Evidence，Token 正常；旧“每 Card 最多4条 Evidence”拒绝了一张表的9条独立数据。放宽到12条后离线重验仍因 claim 写入未引用的 `7.66` 失败。

结论：中型整篇单批在 Token 和输出规模上可行，主要风险是表格损坏和模型没有严格绑定所选 quote。

### 23 Card 中型论文

论文：`川江滚装运输发展的SWOT分析及对策`

- `medium23-20260721`：完成 Evidence、claim 门禁和综合，最终仅因两条政策/预测被字段职责门禁判为背景而失败。
- 自动处置没有擅自删除，生成2项人工任务。跨运行回看确认这是 SWOT/政策分析的字段定义缺口，因此已修正定义和核验上下文。
- `medium23-role-context1-20260721`：新的抽取结果有4项 claim 双轮不一致。3项可由同引文内逐字分句顺序确定性证明；1项把“建议考虑建立”写成“建议建立”，现由限定词合同在 Evidence 抽取阶段直接拒绝。

结论：字段职责和逐字门禁的假阳性已有窄规则处理；模态词丢失保持显式失败。

### 82 Card 大论文

论文：`考虑翻坝和天气的长江班轮运网鲁棒优化模型`

旧 v2 运行 `llm-v4-stability-v2-large82-idfix1-20260721`：

- 9个证据批次，6批成功、3批失败。
- 失败：数值未进入所选引文、跨 Card quote_id 错配、单条 Evidence 使用12条 citation。

v3 运行 `llm-v4-stability-v3-large82-cap12-20260721`：

- 19个证据批次，最大12 Card；全部请求 `finish_reason=stop`，无 reasoning 内容，未见 Token 截断。
- 19批合计输入134,908 tokens、输出39,762 tokens；本地与服务端 prompt token差值均为0，最高单批仅使用57.7%的计划输出预算。
- 原始不可变结果：13批成功、6批失败，运行状态 `partial`。
- 代码修正后离线重验：3个原失败批次可证明有效，等价于16批有效、3批真实失败。
- 真实失败：
  - claim 写入“表6.2”，所选表格行 quote 没有表号；

- 运行约二十余分钟；250 Card 只读规划为45个证据批次，吞吐成本需要关注。

## 全语料规划与测试

- 规划审计：`planning-v3-identity-cap-20260721`。
- 17条论文记录，16篇可规划；490张 Card 全部且唯一覆盖。
- 14篇为整篇单批，82 Card 与250 Card两篇按章节拆分。
- 总证据请求数78；规划失败0。
- 完整测试执行180项，179项首次通过；1项因 Windows 原子替换临时文件偶发 `PermissionError` 失败，单独重跑通过。

## 尚未解决的问题

1. 同一批中模型仍可能把另一张 Card 的 quote_id 放进当前 material_result。
2. 模型仍可能从 Card 全文读取数值或单位，却没有把对应 quote_id 全部放入 citations。
3. 严格一次生成会使少量 Evidence 合同违约阻断整篇综合；在大论文中该概率随批次数累积。
4. 继续缩小批次不能解决表头/单位漏引，且会显著增加82/250 Card论文的耗时。

## 下一项需要决策

是否把“一次受约束的失败批修正”正式纳入 Evidence 抽取协议：

- 只处理首次响应中合同失败的 material_result，不重跑成功 Card。
- 输入仅包含原失败输出、对应 Card、合法 quote candidates、精确错误代码和错误路径。
- 只允许修正 citation 绑定、保留限定词、拆分超限 Evidence 或删除未被引文支持的 claim 片段；不得新增 Card、事实或 quote_id。
- 最多一次；修正后重新执行完整 Schema、覆盖、数值、限定词和 quote归属校验。
- 原响应、修正响应和差异全部存档；第二次仍失败则整篇保持失败，不进入人工裁决或自动循环。

这不是静默兜底，而是可审计的第二阶段协议；但它改变了此前“任何首次失败都立即终止”的约束，需要用户明确同意后才能实施。

## 2026-07-22 决策后实施结果

用户已明确选择加入一次性修正。当前实现状态如下：

1. 运行边界
   - 首次响应和首次失败结果不改写。
   - 只修正可定位的失败 `material_result`，每个原 Evidence 只能 `keep/replace/delete` 一次。
   - 已知失败 Evidence 不能 `keep`；当前 Card 全部合法引文都不支持的数值片段不能继续出现在 replacement 中。
   - 修正请求完成后全量重验；第二次失败终止，不循环。

2. 82 Card 历史失败回放
   - 最终独立回放：`corr82-real-v4-20260722`。
   - 历史失败6批；当前规则直接通过3批。
   - 表号批：4张表 Card、19个原 Evidence 执行收窄，删除引文中没有的表号，整批38个 Evidence 重验通过。
   - 跨 Card 批：修正1个 OCR空格编码单元，删除1个实际属于相邻 Card 的单元。
   - 百分比批：3个失败 Evidence 全部 replace，其中首个拆成2条；删除数据行逐字引文没有提供的百分号。
   - 最终3个待修正批次全部有效，未解决0批。

3. 审计与复用
   - 修正请求与原请求均进入 manifest 和 token 账本。
   - 原批次写 `resolution.json`，运行写 `audit/evidence_corrections.jsonl`。
   - 子运行可复用原批次与修正批次的完整链，仍会重新读取已验证输出。
   - 专用回放脚本只读历史运行，可显式复用既有修正响应并按当前合同重新验证，不修改历史目录。

4. 仍需决策的语义边界
   - 当前数值合同要求 `66.2%` 在所选逐字引文中作为整体出现。表头 quote 中有 `%`、数据行 quote 中有 `66.2` 时，二者不会自动组成百分比事实。
   - 本次严格修正删除了 `%`，得到“水路运量为66.2”。该陈述不越过逐字引文，但丢失了表头提供的单位语义。
   - 若要保留“66.2%”，下一步必须正式定义表格列身份、表头与数据行的复合引用及其确定性验证；不能仅放宽数值字符串检查。

因此，本审计原先提出的“一次受约束修正”决策已经执行并通过当前真实样本。下一项决策转为：**是否把表头与数据行定义为可组合的结构化表格证据。** 在该决策之前，系统维持严格策略并显式丢弃未逐字绑定的单位，不把表头语义暗中拼接进 claim。

## 2026-07-22 表格复合证据决策执行结果

用户已选择把表头与数据行定义为可组合的结构化证据。实现不是放宽字符串检查，而是增加可证明的表格结构和引用合同：

1. 代码先从表格 Card 的精确完整行引文中识别表头、数据行、列数和表格组。
2. 只有表头明确给出 `%`、数据行同列给出裸数值且结构无歧义时，才登记百分比复合候选。
3. 模型若输出该百分比，必须同时选择表头与完整数据行；只引数据行或只引表头均失败。
4. 每个单元格事实只能出现一次；换一种措辞不能绕过重复检查。
5. 排序结论必须覆盖表头和全部比较行，否则只能改成单点陈述。

目标表格批次经过多轮不可变开发回放暴露了三个真实问题：缩写行名误伤、排序陈述证据不完整、同一单元格以不同措辞重复。规则和 Schema 逐项收紧后，最终回放 `corr82-table-contract-v2-20260722` 完成且未解决项为0，共保留8条合格表格 Evidence。另一张船型参数表用 `corr82-table-header-cross-v1-20260722` 独立验证，原2条宽泛输出拆为5条具有表头/数据行双引用的 Evidence。

全语料表格审计 `table-composite-20260722-v2` 显示：490张 Card 中99张为表格，29张含百分号，2张规则表格能确定性建立24个百分比复合事实。这个数字不是覆盖率承诺，而是严格证明范围；单位列、多行错位表头、超长 quote 拆行等结构均没有被猜测性接纳。

历史82 Card运行按当前合同重验19批：14批通过、5批失败。其中一批新暴露的普通表格已通过修正闭合；另一批船期表的表头与数据行分别为9列和10列，必须假设 MinerU 漏掉首个空表头单元格才能对齐，现保持 `citation.table_numeric_scope_unprovable`。这构成当前需要人工验收的边界：规则表格自动处理，解析损坏且需要结构修复的表格阻断，不进入自动 Evidence 修正。
